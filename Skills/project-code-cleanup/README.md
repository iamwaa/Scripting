# Project Code Cleanup

`project-code-cleanup` 是一个用于代码修改后的收尾清理 skill。它不会强制引入新的格式化方案，而是指导 agent 优先使用项目已有的 formatter、linter、typecheck 或测试命令，对本次改动过的代码做小范围、低风险的整理。

## 适用场景

当 agent 完成代码新增、修改或重构后，可以使用这个 skill 做最后一轮检查。它适合处理这些问题：

- 代码格式不统一
- import、变量、函数、类型或组件未使用
- 存在临时调试代码
- 注释过多、过时、重复解释代码含义
- 本次修改后可能留下 lint 或类型诊断问题

如果任务只是阅读、解释或代码审查，并且用户没有要求修改文件，一般不需要使用这个 skill。

## 核心原则

### 1. 保持行为不变

清理的目标是让代码更整洁，而不是重新设计实现。不要因为清理而修改公共 API、路由、数据库字段、导出符号、用户可见文案或业务行为。

### 2. 优先使用项目现有工具

在清理前，agent 应先查看项目已有配置，例如：

- `package.json`
- `.prettierrc`
- `eslint.config.*`
- `.eslintrc*`
- `biome.json`
- `pyproject.toml`
- `ruff.toml`
- `go.mod`
- `Cargo.toml`

如果项目已经提供 `format`、`lint`、`typecheck`、`check` 或测试脚本，应优先使用这些命令。没有配置工具时，再按周围代码风格做手动整理。

### 3. 谨慎移除未使用代码

可以移除明确未使用的内容，例如：

- 未使用的 import
- 未使用的局部变量
- 未使用的私有函数
- 未使用的类型或接口
- 明显无效的死分支
- 当前改动留下的临时调试代码

对于导出的符号、框架约定入口、动态引用、反射、依赖注入、序列化字段、路由文件和测试夹具，应保持保守，不能仅凭当前文件看不到引用就删除。

### 4. 整理注释

应删除这些注释：

- 只是复述代码含义的注释
- 已经过时的注释
- 被注释掉的旧代码
- 当前修改留下的临时说明
- 不再准确的 TODO 或调试备注

应保留这些注释：

- 解释复杂意图
- 说明业务规则
- 记录边界条件
- 说明兼容性原因
- 解释外部 API 的特殊行为
- 提醒维护者不要改动某个看似多余但实际必要的逻辑

必要注释推荐使用行注释格式：

```ts
// 中文内容注释
```

**所有必要注释必须使用中文。** 如果现有注释是英文，应在清理时改为简短的中文注释。

## 推荐工作流程

1. 确认本次改动涉及的文件。
2. 查看项目已有格式化、lint、类型检查或测试配置。
3. 运行项目现有格式化命令，或按周围风格手动格式化。
4. 根据诊断、lint 输出和搜索结果移除明确未使用的代码。
5. 删除不必要注释，将必要注释整理为简短的 `// 中文内容注释`。
6. 运行最小必要验证，例如单文件诊断、lint、typecheck 或相关测试。
7. 查看最终 diff，确认没有引入无关重构或大范围格式化噪音。

## 使用示例

用户可以这样要求 agent：

```text
修改完代码后，请使用 project-code-cleanup 做一次收尾清理。
```

也可以这样描述更具体的需求：

```text
帮我清理这次改动：格式化代码，删除未使用 import 和变量，非必要注释不要保留，必要注释改成 // 中文内容注释。
```

## 输出建议

完成清理后，agent 的最终回复应简洁说明：

- 做了哪些格式化或清理
- 是否移除了未使用代码
- 是否调整了注释
- 运行了哪些检查
- 哪些检查因为环境或依赖原因无法运行

不要逐条列出每一个空格、换行或微小格式变化，除非用户明确要求。

## 文件结构

```text
project-code-cleanup/
├── SKILL.md

└── skill.json
```

## 注意事项

- 不要清理生成文件、压缩文件、第三方 vendored 代码或 lock 文件，除非用户明确要求。
- 不要为了通过 lint 随意删除业务逻辑。
- 不要把大范围格式化混入小修复，避免最终 diff 难以审查。
- 不要移除 license header、生成文件说明或文档生成器需要的注释。

## 与其他 Skill 的关系

- **project-auto-backup**：在修改代码之前，应先使用备份 skill 保存当前项目，尤其是大型重构时。
- **project-file-organization**：创建新文件或整理项目结构时，应遵循文件摆放规范 skill 定义的目录结构和命名约定。
