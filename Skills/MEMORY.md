# MEMORY.md

Long-term curated memory for this agent/workspace.

- Before editing or generating files in a project, use the `project-auto-backup` skill to back up the current project first when feasible. Skip for read-only tasks.
- After modifying or generating source code, use the `project-code-cleanup` skill before the final response: format touched code, clean unnecessary comments, remove clearly unused code/imports, and run the narrowest useful checks. Preserve explicit TODOs or placeholders marked for future use. Single-file size thresholds: 200+ lines = watch for oversized functions/components; 300+ lines = mandatory structure review, not automatic splitting; 500+ lines = split unless there is a strong cohesion or behavior-risk reason; 800+ lines = almost certainly split unless it is generated-style data/config or another rare cohesive exception. Split when a file mixes responsibilities or has clear extraction boundaries; keep it together when it is a cohesive complex page, dense declarative UI, schema/config, generated-style data, or splitting would increase risk. If not splitting a 300+ line touched file, document the reason.
- For Scripting projects, when creating or moving files/directories such as pages, components, hooks, utils, services, constants, types, api modules, assets, or reorganizing project structure, follow the `project-file-organization` skill's directory conventions. During both new project generation and later edits, run its `scripts/check.py` when feasible if any touched source file reaches 300+ lines. Use the result to decide by responsibility: extract `types`, `constants`, `utils`, `services`, reusable `components`, and separate `pages` when the file mixes those concerns. For 500+ line touched files, prefer splitting unless there is a strong reason to keep them cohesive; for 800+ line touched files, split unless there is a rare explicit exception. If only editing existing files without adding/moving files and touched files remain under 300 lines, this skill is usually unnecessary.
- For Scripting projects, when creating or editing `alarm_live_activity.tsx` files, follow the `AlarmLiveActivity` documentation and DEMO style. Use `buttonStyle="glass"` or `buttonStyle="glassProminent"` for buttons on iOS 26 as recommended in the documentation.
- All necessary code comments MUST be in Chinese: `// 中文内容注释`, unless preserving required license headers, generated-file notices, documentation format, or external project conventions.
- Typical project-edit workflow: backup → edit/create files → run relevant verification → cleanup. Add `project-file-organization` structure checks for Scripting projects when files/directories were created, moved, reorganized, or a touched source file reaches 300+ lines. For newly generated Scripting apps, check line counts before final response; if `index.tsx` is 300+ lines and mixes types, utilities, services, components, and pages, split it. If it is a cohesive single page/tool and keeping it together is clearer, keep it and state why.
